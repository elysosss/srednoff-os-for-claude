## Goal

Превратить SREDNOFF OS из системы, перекошенной в маркетинг/SEO/бизнес, в слой, который
реально ускоряет **программиста**, и при этом не мешает: убрать ложные блокировки хуков,
сократить постоянно загружаемый контекст, закрыть дыры в скиллах для инженерной работы.

## User value

Три конкретные боли, названные владельцем форка, и что считается их закрытием:

| Боль | Сейчас | Закрыта, когда |
|---|---|---|
| «Блокал вместо `.env` — `.env.example`» | Хук денит легитимные файлы, доверие к системе падает, её выключают | Ноль ложных блокировок на шаблонных/примерных файлах, регрессия закрыта фикстурой |

| «Скиллов для программиста мало» | См. замеры ниже — их действительно мало | Инженерные домены закрыты установимыми скиллами не хуже, чем сейчас закрыт SEO |

## Current state (замерено, не на глаз)

**1. Баг `.env.example` — подтверждён в коде.**
`.claude/hooks/protect-secrets.ps1:26` и `.claude/hooks/protect-secrets.sh:25` содержат
идентичный паттерн:

```
(^|[\\/])\.env(\.|$)|id_rsa|id_ed25519|\.pem$|\.key$|secrets?\.(json|ya?ml|toml)$|credentials(\.json)?$
```

Ветка `\.env(\.|$)` матчит `.env.` → под запрет попадают `.env.example`, `.env.sample`,
`.env.template`, `.env.local.example`, `.env.dist`. Это файлы, которые **положено**
коммитить и редактировать. Хук при этом `deny`, а не `ask` — обойти в моменте нельзя.
Отдельно: паттерн ловит `Read` тоже, то есть агент не может даже прочитать `.env.example`,
чтобы понять, какие переменные нужны проекту.

## Assumptions

- Форк остаётся форком: авторство апстрима (`LICENSE`, `owner` в `.claude-plugin/`,
  «Made by» в README) не трогаем — это прямо запрещено `FORK.md`.
- Фиксы, полезные всем (баг `.env.example`, дрейф доков), идут **апстримом через PR** —
  так велит `FORK.md`. Programmer-специфичное расширение может остаться fork-local.
- Windows/PowerShell — основная платформа владельца, но парность `.ps1`/`.sh` обязательна:
  её проверяет CI, сломать её = уронить сборку.
- Бюджет контекста важнее полноты: скилл, который никогда не сработает, — это чистый
  расход токенов на его name+description каждую сессию.

   `deny → ask` не делаем (отклонена — это чужой продуктовый выбор, не наш).
4. **Контекст** → **ядро + по требованию.** ~50–70 строк жёсткого ядра в постоянной
   загрузке, остальное читается когда нужно. Русский язык сохраняем. Нормативное
   содержание не теряется — только перестаёт грузиться каждую сессию.

## Architecture

Ничего в архитектуре слоёв не ломаем — она здравая. Меняем наполнение трёх слоёв:

```
CLAUDE.md + rules/00-90     → СЖАТЬ: ядро всегда, детали по требованию
skills-library/ (309)       → ДОБАВИТЬ инженерные домены, возможно вычистить мёртвое
hooks/ (6 пар)              → ТОЧНОСТЬ: убрать ложные срабатывания, разделить deny и ask
registry/CORE-300.md        → без изменений (текстовый справочник, грузится грепом)
```

Принцип отбора новых скиллов: **устанавливаемое содержимое, а не ссылки**. Скилл входит в
библиотеку, только если у него есть рабочий `SKILL.md` с воспроизводимым воркфлоу,
совместимая лицензия и он не дублирует канон из `CAPABILITY-INDEX.md`.

## Data model / migrations

Нет БД. «Миграции» здесь — формат `skills-library/index.json` и frontmatter скиллов:
любое изменение схемы обязано пройти `validate-skills-library.{ps1,sh}` и
`gen-catalog-json` drift-gate в CI.

## API contracts

Контракт хуков Claude Code (`hookSpecificOutput.permissionDecision` для PreToolUse,
`decision: block` для UserPromptSubmit) — менять нельзя, только содержимое решений.
Контракт `SKILL.md` (frontmatter `name` + `description`) — проверяется валидатором.

## Security model

Ослабление хука — это изменение защитного контроля, а не косметика:

- `.env.example` разрешаем **по имени файла**, но контентная проверка
  (`Find-SecretSignals`) остаётся включённой: если в `.env.example` лежит настоящий ключ,
  блокировка обязана сработать. Это ключевое требование к фиксу.
- Каждое послабление сопровождается фикстурой `expectMatch: false` для легитимного случая
  **и** сохранением `expectMatch: true` для реального секрета в файле с тем же именем.
- Новые скиллы из внешних источников проходят верификационный гейт правила `70`:
  лицензия, дата коммита, скан содержимого. `WSH`/`VOLT`/`GH`/`EXT` — unvetted по умолчанию.

## Находка, меняющая объём работы: скиллы не установятся сами

Обнаружено при проверке отчёта агента B. `scripts/gen-profile-lock.{ps1,sh}` — это то, что
подбирает скиллы под проект по тегам. Его эвристика классификации (`gen-profile-lock.sh:37-65`)
для нашего стека почти слепа:

| Что в проекте | Какие теги ставит сейчас |
|---|---|
| `requirements.txt` / `pyproject.toml` | только `backend` (+`trading`/`ml`+`data`/`telegram` по содержимому) |
| `Dockerfile` в корне **или** любой `*.tf` | `infra` + `devops` |
| `package.json` | `web`, `frontend` (+3d/animation/ai/design/telegram) |
| имя папки содержит `seo`/`amazon`/`ppc`/… | соответствующие бизнес-теги |

Не детектируется вообще: `docker-compose.yml` без Dockerfile, `.github/workflows/`,
каталог `k8s/`, `Makefile`, `alembic.ini`, `pytest.ini`/`tox.ini`, `poetry.lock`/`uv.lock`,
`manage.py` (Django), `*.sql`. Теги `test`, `quality`, `perf`, `ops` не выставляются
**никогда** — ни одной веткой эвристики.

Плюс словарь тегов: в `skills-library/index.json` теги `lang` и `cicd` не используются
ни разу (проверено), хотя в `CORE-300.md` они в списке доменных тегов. Скилл с тегом
`[lang]` не будет подобран никогда.

**Вывод:** добавить скиллы недостаточно — без правки детекции они лягут мёртвым грузом.
Это отдельный, самостоятельный и хорошо продаваемый апстриму PR: «gen-profile-lock плохо
распознаёт Python/DevOps-проекты». Делать его надо **раньше** скиллов, иначе нечем будет
показать, что новые скиллы вообще подхватываются.

Следствие для Фазы 3: теги новым скиллам берём только из тех, что эвристика реально умеет
выставлять (`backend`, `data`, `infra`, `devops`, `test`, `perf`, `quality`, `security`,
`ops`), а недостающие из них — учим её выставлять тем же PR.

## Отчёт агента D — хуки. Две дыры в безопасности, а не только ложные срабатывания

Полный отчёт с готовыми блоками кода и 41 фикстурой: `scratchpad/D-hooks.md`. Прогнан 71 кейс.

### Дыры (важнее ложных срабатываний — их я перепроверил лично)

**SEC-1. В bash-порте правило `private_key` не срабатывает никогда.**
`hook-lib.sh:35` вызывает `"$GREP_BIN" -Pq "$pattern"` **без `--`**, а паттерн
`private_key` начинается с `-----`. grep принимает его за опцию. Воспроизведено:

```
$ printf 'x-----BEGIN RSA PRIVATE KEY-----y\n' | grep -Pq "-----BEGIN [A-Z ]*PRIVATE KEY-----"
grep: unknown option -- ---BEGIN [A-Z ]*PRIVATE KEY-----
exit=2
```

Ошибка глушится `2>/dev/null`, ненулевой код читается как «совпадений нет» → allow.
Итог: на Linux/macOS приватный ключ не блокируется ни при записи, ни в команде, ни в
промпте. В PowerShell блокируется. Фикс — один символ: `-Pq --`.

**SEC-2. Вся контентная защита bash-порта отключается сменой локали.**
Тот же прогон, уже с `--`:

```
$ printf '…' | grep -Pq -- "-----BEGIN [A-Z ]*PRIVATE KEY-----"
grep: -P supports only unibyte and UTF-8 locales
exit=2
```

При `LC_ALL=C` (обычное дело в CI-контейнерах, cron, systemd) **все** секрет-правила
молча возвращают пусто — полный fail-open. `doctor.sh` проверяет только `jq`
(`doctor.sh:29-38`), проверки `grep -P` нет. Фикс: `LC_ALL=C.UTF-8` в `hook-lib.sh`,
self-test при старте, новая проверка `grep-pcre` в doctor. Здесь же готовый аргумент для
апстрима: комментарий на `doctor.sh:29` показывает, что автор уже закрывал ровно такой
класс бага для `jq` — это его собственный прецедент.

**SEC-3. `MultiEdit` и `NotebookEdit` не сканируются вообще.** Оба матчера прописаны в
`settings.example.json`, но `protect-secrets.*` читает только `content`, `new_string`,
`old_string` — массив `edits[]` и `new_source` не читаются. Секрет через `MultiEdit`
проходит. Проверено по коду (`protect-secrets.ps1:32`) и прогоном агента.

Прочие дыры покрытия из прогона: `Bash: cat .env` → allow; `rm -rf "$HOME"` → allow;
`rm -rf --no-preserve-root /` → allow.

### Ложные срабатывания (13 классов, все воспроизведены прогоном)

Помимо `.env.example` и родни: `id_rsa.pub`/`id_ed25519.pub` (**публичные** ключи),
`ca-bundle.pem`/`fullchain.pem`, `docs/deck.key`, k8s `sealed-secrets.yaml` и
`external-secrets.yaml` (это контроллеры, а не секреты), `tests/fixtures/fake_credentials.json`.

Особенно вредные для нашего стека:

- **`docker-compose.yml` и `alembic.ini` с плейсхолдером** `postgres://user:password@db` —
  deny по `db_connection_string`. Оно же ловит `postgres://${DB_USER}:${DB_PASS}@…`, то
  есть **правильно написанный** compose. При этом `postgresql+psycopg2://` с настоящим
  паролем не ловится вообще — паттерн `postgres(ql)?` не допускает `+driver`.
- **Ветка `feature/disk-cleanup-and-cache-invalidation-rework`** — deny как
  `openai_api_key`: подстрока `sk-` внутри слова матчится, левой границы у паттерна нет.
- **Удаление захардкоженного ключа блокируется.** `protect-secrets` сканирует `old_string`
  — то есть текст, который вы **убираете**. Попытка вычистить `AKIA…` из кода = deny.
  Он же денит правку собственных фикстур репозитория.
- **`git push origin main && docker compose up -d`** — deny: детектор `--force` не
  привязан к самой команде push, ловит флаг где угодно в строке.
- **`grep -rn 'git reset --hard' docs/`** и `cat docs/mkfs-notes.md` — deny: опасные слова
  ищутся в любой позиции, а не в командной.

Один случай агент честно оставил без фикса: поддельный JWT в фикстуре неотличим от
настоящего — предложено задокументировать, а не «чинить».

### Расхождения `.ps1` / `.sh` (парность нарушена)

Кроме SEC-1: PowerShell `-match` регистронезависим, `grep -P` — нет, поэтому
`akiaiosfodnn7example` в нижнем регистре денится в PS и проходит в SH. Паттерн `rm` имеет
левую границу в `.sh` и не имеет в `.ps1`. Плюс мелочи в сигнатурах ledger и
`mark-profile-lock-read` (regex против glob).
