# C2: Опциональное сжатие контекста — исследовательская спека

> Статус: DRAFT
> Тип: спека-набросок (исследовательская: сначала замер, потом решение, строить ли вообще)
> Модуль E1: `squeeze` (только если фаза M1 даст зелёный свет)
> Зависит от: E1 (формат модуля, конвейер tool-io), F1 (порядок переписывания), C1 (запрет трогать префикс и историю)   Блокирует: —

## Goal
Выяснить на реальных задачах владельца, сколько контекста можно снять сжатием вывода инструментов **на стороне хуков и файлов** (не прокси), чего это стоит в точности, и только при измеренной выгоде поставить выключенный по умолчанию модуль.

## User value
Заявленные цифры — 15–95 %, 59–70 %, «−89 % в среднем» — сняты на чужих данных и частично вообще не измерены. Боль владельца: непонятно, стоит ли тащить прокси-комбайн ради экономии. Закрыто, когда есть таблица «заявлено / измерено на моих транскриптах / решение», и решение подкреплено числами, а не маркетингом.

## Non-goals
- **Никакого прокси для трафика Claude.** `ANTHROPIC_BASE_URL` не выставляется никогда (PF-18); OAuth подписки в сторонних прокси запрещён условиями Anthropic. Это исключает штатные режимы всех четырёх изученных инструментов.
- Не переписываем историю задним числом (старение/суммаризация старых ходов): ломает кэш (C1).
- Не сжимаем CLAUDE.md, правила, память — это «один канон», текст для людей, и он кэшируется по сниженной цене чтения из кэша.
- Не сжимаем выход модели (terse-стили) — это вопрос качества ответа, не контекста.

## Current state
В OS ничего для сжатия нет. Платформа уже делает часть работы сама: вывод Bash длиннее ~30 000 символов сохраняется в файл, модель получает путь и превью до 2 000 символов (доки `tools-reference` → Output limits; в этой же сессии наблюдалось как `Output too large ... Full output saved to ... Preview (first 2KB)`). Порог настраивается `bashOutputMaxChars` (v2.1.261+) — доступно в desktop 2.1.281, недоступно в CLI 2.1.177 (PF-01). Официальная страница `costs.md` сама рекомендует паттерн «PreToolUse-хук оборачивает команду фильтром» (раздел Offload processing to hooks).

Выводы из базы:
1. **Хвост решает.** Результатов > 8 000 символов — 95 из 2 623 (3,6 %), а символов у них **42,5 %**. Всё, что ниже p90, сжимать бессмысленно.
2. **Вывод Bash почти никогда не доходит до штатного порога 30k** (max 27 202) — штатный спилл у владельца фактически не срабатывает.
3. **Семейства команд не те, под которые заточен RTK.** Тесты/сборки/линтеры (сильная сторона RTK: −80…−99 %) почти отсутствуют. Крупнейшие по объёму — чтение файлов через шелл (`cat`/`sed`/`head` ≈ 18 % всех символов), `gh`/GitHub API ≈ 6,5 %, `grep` ≈ 6 %, `curl` ≈ 1 %.
4. **Потолок выгоды.** Каждый результат перечитывается каждым следующим ходом до компакции. Взвешенно по ходам результаты инструментов — **13,7–18,2 %** всех входных токенов основной сессии (при 4,0–3,0 символа на токен; всего 456 M входных токенов, 98,4 % из них — чтение из кэша). Результаты > 4 000 символов — **8,0–10,6 %**. Значит, даже идеальное сжатие крупных выводов снимает не больше ~10 % входа, а реалистичное сжатие вдвое — **~4–5 %**.

## Architecture (дизайн)
### Протокол замера (M0–M3), ни одна фаза до M3 не меняет поведение
- **M0 — база** (сделано выше, повторяемо скриптом `bin/squeeze-measure`): доли по инструментам и семействам, хвост, потолок взвешенно по ходам.
- **M1 — офлайн-реплей.** Кандидаты-компрессоры как чистые функции применяются к сохранённым выводам из транскриптов: (a) симуляция штатного спилла при порогах 4k/8k/16k с превью 2k; (b) дедуп повторяющихся строк + окно «голова/хвост» для логов; (c) табличное сжатие JSON-массивов (`gh api`); (d) группировка `grep` по файлу; (e) для сравнения — headroom как библиотека в отдельном процессе (если разрешено, Вопрос 1). Метрики на кандидата и семейство: доля снятых символов; вклад во взвешенный вход; **удержание цитат** — доля строк-«иголок» (пути, `path:line`, идентификаторы, коды ошибок, числа ≥ 3 знаков), которые модель процитировала в следующем ответе и которые пережили сжатие; прогноз дочитываний — доля случаев, где процитированное лежит вне превью.
- **M2 — тень.** Модуль в режиме `shadow`: PostToolUse считает сжатие, пишет в `.state/shadow.jsonl` только размеры, семейство и `tool_use_id`, **возвращает пустой вывод** — модель видит оригинал. Удержание цитат считается офлайн джойном с транскриптом. Две недели или ≥ 300 крупных выводов.
- **M3 — живое A/B** по согласию владельца: чередование по сессиям. Метрики из транскриптов: входные токены на ход, ходов на задачу, дочитывания спилла, повторные запуски той же команды (признак потери), число компакций; оценка задачи владельцем одной строкой в журнале.
- **Порог принятия** на компрессор: ≥ 30 % символов своего семейства, удержание цитат ≥ 98 %, вклад ≥ 2 % взвешенного входа. Иначе — запись `rejected` с числами в журнал наблюдений. Стоп-правило M3: повторных запусков/дочитываний из-за сжатия > 5 % — выключить.

### Каналы (в порядке предпочтения, дешёвое первым)
- **K0 — штатный рычаг.** `bashOutputMaxChars` в проектных настройках (только desktop). Ноль кода; M1(a) показывает, достаточно ли его.
- **K1 — обёртка команды** (паттерн RTK и `costs.md`): PreToolUse(Bash|PowerShell) для белого списка семейств подменяет команду на `squeeze-run -- <команда>`; фильтр — отдельный процесс, сырой вывод пишется в спилл. Переписывается вход, не выход.
- **K2 — переписывание вывода**: PostToolUse `updatedToolOutput` для Bash/PowerShell/Read/Grep/WebFetch/MCP с маршрутизацией по типу контента; результат обязан пройти схему (PF-02, A-05), иначе платформа молча отдаст оригинал — это безопасный отказ, но его надо считать в метриках. Только в момент вставки, никогда задним числом.

### Композиция с F1 (A-03)
Два хука, переписывающие один вызов, конфликтуют. Требование к E1: **один диспетчер tool-io** на пару (событие, инструмент); модули объявляют стадии в `metadata.srednoffOs.toolIo` с номером порядка, диспетчер гонит их последовательно. Порядок: вход — `squeeze` (обёртка видит плейсхолдеры F1 и лишь добавляет префикс) → F1 (раскрытие, ближе всех к исполнению); выход — `squeeze` → F1 (маскирование последним, ближе всех к модели). Пока диспетчера нет: при включённом F1 модуль `squeeze` принудительно работает в `shadow` и говорит об этом.

### Отвергнуто
Любой прокси (OmniRoute, OmniGlyph, `headroom wrap/proxy`, прокси Caveman) — ограничение 1. Старение истории (OmniRoute Aggressive) — ломает кэш. Сжатие CLAUDE.md/правил (`/caveman-compress`) — «один канон». Контекст-как-картинка — прокси и зависимость от модели.

## API contracts (интерфейсы и форматы)
`config/default.json`: `{"enabled": false, "mode": "off|shadow|on", "channels": {"wrap": false, "rewrite": false}, "minChars": 8000, "families": ["cat","sed","head","grep","gh","curl"], "maxPreviewChars": 2000, "spillTtlDays": 7}`. Маркер в сжатом выводе: `[squeeze: 41 230 -> 3 900 chars; full: .claude/os-modules/squeeze/.spill/<sha256>.txt]`. `squeeze-measure[.ps1|.sh] [--since 30d] [--json]` → таблицы M0/M1, коды выхода 0/2. `shadow.jsonl`: `{ts, tool, family, tool_use_id, before, after, compressor}` — без текста.

## Data model / migrations
`.spill/` — сырые выводы, gitignored, удаляются по TTL скриптом при SessionStart; `.state/shadow.jsonl` — только числа. Миграций нет: модуль новый.

## Security model
Спилл хранит **немаскированный** вывод на диске проекта — тот же класс риска, что транскрипт (A-02). Дочитывание спилла идёт через Read и проходит F1. Защищаем: спилл вне git, TTL, в `shadow.jsonl` нет содержимого. Не защищаем: локальный доступ к диску. Внешний движок (если разрешат) — только закреплённая версия после гейта правила 70, без сети.

## Risks
| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Сжатие выкинуло нужную строку, модель делает неверный вывод молча | средняя | высокое | порог удержания 98 %, маркер с путём к оригиналу, стоп-правило M3 |
| Выгода меньше стоимости поддержки (потолок ~10 %) | высокая | среднее | решение принимается после M1; отказ — законный исход |
| Латентность PowerShell-хука на каждом Bash | средняя | среднее | фильтр `if`, exec-форма, только семейства из списка |
| Конфликт с F1 | высокая без диспетчера | высокое | принудительный `shadow` до появления диспетчера E1 |
| Схема встроенного инструмента отвергла замену | средняя | низкое | считается в метриках как «не сработало» |

## Acceptance criteria
- AC1: при `enabled=false` и `mode=off` вывод бит-в-бит равен оригиналу, файлов состояния нет — S1.
- AC2: `shadow` не меняет вывод и пишет только числа — S2.
- AC3: `on` сжимает крупный вывод, оригинал доступен по маркеру — S3.
- AC4: без диспетчера при включённом F1 модуль уходит в `shadow` — S4.
- AC5: `squeeze-measure` на фикстурах даёт ожидаемые числа без текста — S5.

## Rollback plan
`enabled=false` — хуки выходят первой строкой. Удаление: снять стадии из диспетчера, удалить `.claude/os-modules/squeeze/` вместе со `.spill/`. Данные, от которых что-то зависит, не создаются.

## Estimate (оценка объёма)
