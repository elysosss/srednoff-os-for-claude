# E1: Формат модуля OS и шаблон создания

> Статус: DRAFT — вопросы решены 2026-09-27
> Тип: полная спека (минимальная — ровно столько, чтобы F1 было куда класть)
> Модуль E1: не модуль (это сам формат)
> Зависит от: —   Блокирует: F1, и через него всё остальное

## Goal

Единый формат расширения OS: один каталог с манифестом, хуками, навыками, командами,
конфигом и тестами, который ставится в проект одной командой, включается и выключается
флагом и удаляется без следов. F1 — первый модуль в этом формате.

## User value

Сейчас каждое новое свойство OS размазывается по `.claude/hooks`, `settings.example.json`,
`doctor`, `README` и `version.json` руками, а выключить его можно только правкой
`settings.json`. После E1:

- расширение живёт в одном каталоге и видно целиком;
- `os-module enable f1 --project .` / `disable` / `uninstall` — без ручной правки JSON;
- выключенный модуль не меняет поведение OS ни на байт (требование брифа «опциональность»);
- `doctor` сам находит проверки модуля.

## Non-goals

- Маркетплейс, реестр модулей, автообновление, подпись пакетов.
- Зависимости между модулями глубже «модуль A требует модуль B» (без версионного солвера).
- Перевод существующих хуков OS (`protect-secrets`, `block-dangerous-bash` и т.д.) в модули.
  Возможно позже, отдельной спекой; сейчас это ломало бы апстрим-совместимость.
- Глобальная установка модулей в `~/.claude`. Запрещена владельцем (HANDOFF §2).

## Current state

- OS разворачивается в проект копированием (`scripts/init-claude-project.{ps1,sh}`): правила,
  навыки, команды, хуки, `settings*.example.json`. **Активный `.claude/settings.json` скрипт
  никогда не создаёт** — хуки включаются руками копированием example-файла.
- Параллельно OS уже упакована как плагин Claude Code: `.claude-plugin/plugin.json`
  (`"hooks": "./hooks/hooks.json"`, `"defaultEnabled": false`). Плагинная проводка работает
  только для bash-хуков: один `hooks.json` не умеет ветвиться по ОС (комментарий в
  `hooks/hooks.json`).
- Состояние хуков OS живёт вне репозитория: `~/.claude/logs/hook-events.jsonl`,
  `~/.claude/logs/session-state/<session_id>/`. Это прецедент для места под состояние модулей.
- Версия OS — `registry/version.json` (`v1.20`), фичи перечислены в `features`.
- Парность `.ps1`/`.sh` проверяет CI; кириллица в `.ps1` запрещена (урок v1.12).

## Assumptions

- Хуки модуля — в **`.claude/settings.local.json`** проекта (машинно-локальный, не
  коммитится): у F1 в команде хука абсолютный путь к бинарю на этой машине. Флаг `--shared`
  переключает на `settings.json`. Решено владельцем (Q1).
- Слияние JSON в PowerShell 5.1 делается штатным `ConvertFrom-Json`/`ConvertTo-Json`
  без `jq` — так же, как Windows-хуки OS обходятся без `jq` сейчас.
- A-03 (конфликт двух хуков, переписывающих один вход/выход) не закрыт — формат обязан
  уметь **обнаружить** такой конфликт при включении, раз не может его разрешить.

## Questions

Решено владельцем 2026-09-27:

1. **Q1.** Хуки модуля — в **`settings.local.json`**; `--shared` переключает на `settings.json`.
2. **Q2.** Плагинного пути установки **нет**: только папка проекта. Каталог модуля остаётся
   совместимым с плагином — отладка через `--plugin-dir` возможна, но установщик ничего не
   пишет в `~/.claude`.
3. **Q3.** В апстрим PR-ами уходит **всё, кроме личных значений**: формат E1, шаблон и сами
   модули. Личные значения (хосты, свои правила с данными) живут только локально, в
   `stateDir`, и в репозиторий не попадают.
4. **Тесты — без behave** (решение по всему пакету): сценарии спек исполняются фикстурами
   `run-evals`, парно `.ps1`/`.sh`.

## Architecture (дизайн)

### Где что лежит

```
srednoff-os-for-claude/                  исходники OS (форк)
├── modules/
│   ├── _template/                       шаблон, из которого `os-module new` делает модуль
│   └── f1-secrets-filter/               первый модуль (спека F1)
└── scripts/os-module.{ps1,sh}           установщик/переключатель, пара как у всех скриптов OS

<project>/                               проект, куда модуль поставлен
└── .claude/
    ├── settings.local.json              сюда сливаются хуки включённых модулей (Q1)
    ├── skills/<module>--<skill>/        навыки модуля, с префиксом — без коллизий с OS
    ├── commands/<command>.md            команды модуля (`/os-filter` и т.п.)
    ├── agents/<module>--<agent>.md      сабагенты модуля (роли D4); ставятся и снимаются
    │                                     вместе с режимом, как навыки и команды
    └── os-modules/
        ├── installed.json               учёт: что, какой версии, какие хуки мы добавили
        ├── .state/<module-id>/          несекретное состояние модуля на проект (отчёты,
        │                                 маркеры); установщик добавляет `.claude/os-modules/.state/`
        │                                 в `.gitignore` проекта и отказывает, если git его не игнорирует
        └── <module-id>/                 копия модуля (без tests/ и src/)
            ├── .claude-plugin/plugin.json
            ├── hooks/hooks.json         шаблон хуков модуля (источник для слияния)
            ├── bin/  scripts/  config/
            └── state.json               флаг режима на проект (off | on | свои режимы)

~/.claude/logs/os-modules/<module-id>/   секретное или машинное состояние модуля вне проекта
                                          (ключи, журналы; прецедент: ~/.claude/logs/hook-events.jsonl)
```

Правило выбора: всё, что может содержать секрет или привязано к машине, — в
`~/.claude/logs/os-modules/<id>/` (`stateDir`); несекретное и привязанное к проекту — в
`.claude/os-modules/.state/<id>/`.

Каталог модуля одновременно **валидный плагин Claude Code** (его можно подгрузить
`claude --plugin-dir .claude/os-modules/<id>` для отладки, PF-17). Установщик OS при этом
плагинный механизм не использует — копирует и сливает хуки в проектные settings, как того
требует запрет глобальной установки.

### Манифест

Официальный `.claude-plugin/plugin.json` + блок `metadata.srednoffOs` (Claude Code его не
читает, PF-17):

```json
{
  "name": "srednoff-os-f1-secrets-filter",
  "version": "0.1.0",
  "description": "...",
  "license": "Apache-2.0",
  "defaultEnabled": false,
  "metadata": {
    "srednoffOs": {
      "schema": 1,
      "id": "f1",
      "kind": "hooks+daemon",
      "osCompat": ">=1.20",
      "claudeCodeCompat": ">=2.1.177",
      "platforms": ["windows", "linux", "macos"],
      "modes": ["off", "detect", "enforce"],
      "defaultMode": "off",
      "config": { "default": "config/default.json", "schema": "config/schema.json" },
      "rewrites": {
        "PreToolUse.updatedInput": ["Edit", "Write", "MultiEdit", "NotebookEdit", "Bash", "PowerShell"],
        "PostToolUse.updatedToolOutput": ["Read", "Bash", "PowerShell", "Grep", "Glob", "WebFetch", "WebSearch", "Edit", "Write", "TaskOutput", "mcp__.*"]
      },
      "requires": { "bins": ["os-maskd"], "modules": [] },
      "doctor": "doctor/checks.json",
      "stateDir": "~/.claude/logs/os-modules/f1",
      "hooksSource": { "windows": "hooks/hooks.windows.json", "default": "hooks/hooks.json" }
    }
  }
}
```

Ключевые поля:

- **`modes` / `defaultMode`** — режимы модуля. Минимум `off`/`on`; F1 объявляет
  `off`/`detect`/`enforce`. Флаг хранится в `.claude/os-modules/<id>/state.json` и
  читается хуками **первым делом** (см. «Контракт хука»).
- **`rewrites`** — какие инструменты модуль переписывает через `updatedInput` /
  `updatedToolOutput`. Нужен, чтобы `os-module enable` **отказал** включать второй модуль,
  переписывающий то же самое (A-03), а `doctor` ловил чужой хук в settings, который делает
  то же вне модулей.
- **`hooksSource`** — отдельный файл хуков для Windows. Это ровно та проблема, которую
  плагинный `hooks/hooks.json` OS не решает («a single plugin hooks.json cannot branch
  per-OS»): установщик выбирает файл по платформе при слиянии.

### Контракт хука модуля

1. Первое действие — прочитать режим. Нет файла, битый файл, `off` → выйти с кодом 0 и
   **пустым stdout**. Это и есть «выключенный модуль не меняет поведение»: для Claude Code
   хук без вывода и с кодом 0 — отсутствие решения (PF-12).
2. Хук вызывается в **exec-форме** (`command` + `args`, PF-14), путь — через
   `${CLAUDE_PROJECT_DIR}`. Шелл не нужен, кавычки не ломаются на пробелах в путях.
3. Модуль сам решает, fail-open он или fail-closed, и **объявляет** это в `config`. Формат
   напоминает: таймаут и падение хука Claude Code трактует как fail-open (PF-12, PF-13), так
   что fail-closed обязан реализовываться внутри хука (свой короткий таймаут + явный
   `deny`/`block`), а не надеждой на Claude Code.
4. Журнал решений — в `stateDir`, формат совместим с `~/.claude/logs/hook-events.jsonl`
   (sha256 входа, без сырого содержимого).

### Установщик `scripts/os-module.{ps1,sh}`

| Команда | Действие |
|---|---|
| `new <id>` | копирует `modules/_template` → `modules/<id>`, подставляет id и имя |
| `list [--project P]` | модули в форке и их статус в проекте |
| `install <id> [--project P]` | проверяет `osCompat`, `claudeCodeCompat`, `platforms`, `requires`; копирует модуль в `P/.claude/os-modules/<id>`; режим = `defaultMode`; **хуки ещё не подключены** |
| `enable <id> [--shared]` | проверяет конфликт `rewrites`; сливает хуки модуля в `settings.local.json` (или `settings.json`); запоминает в `installed.json` ровно добавленные записи; ставит навыки и команды |
| `mode <id> <mode>` | пишет `state.json`; хуки подхватят на следующем вызове, перезапуск не нужен. Переход в `off` дополнительно **убирает** из `.claude/` навыки, команды и агентов модуля (`.claude/agents/<module>--<agent>.md`), переход из `off` — возвращает: эти компоненты Claude Code загружает сам, флаг режима они не читают, и без этого выключенный модуль продолжал бы менять поведение |
| `disable <id>` | удаляет из settings **только** записи из `installed.json`, остальное не трогает |
| `uninstall <id> [--purge]` | `disable` + удаление каталога модуля, навыков, команд; `--purge` дополнительно чистит `stateDir` |
| `status [<id>]` | режим, версия, подключены ли хуки, результат `doctor`-проверок модуля |

Установщик — пара `.ps1`/`.sh` с одинаковым поведением, как остальные скрипты OS; парность
проверяется существующим CI.

Почему отдельный `installed.json`, а не метка в самих хуках: схема settings Claude Code
строгая к обработчикам хуков, посторонний ключ в записи хука — риск, что запись не
загрузится (A-14; если спайк покажет, что ключ допустим, метку можно дублировать в записи).
Пути к скриптам модуля в проводке — через `${CLAUDE_PROJECT_DIR}` (A-13; если не
подставляется — установщик пишет абсолютный путь при `enable`).

```
├── tests/                 пример сценария run-evals «модуль в off не меняет поведение»

```

### Шаблоны CI (для D8)

Модуль может нести шаблоны GitHub Actions в `ci/`, объявленные в
`metadata.srednoffOs.ciTemplates` (`[{source, target}]`, `target` — внутри `.github/`
проекта). `enable` копирует их только по явному флагу `--ci`, никогда не перезаписывает
существующий файл без `--force` и записывает их в `installed.json`; `uninstall` удаляет
только файлы, чей хэш совпадает с установленным (правленные человеком — оставляет и
сообщает). Выключение режима шаблоны CI **не** снимает: CI — серверная защита, и
локальный переключатель модели не должен её отключать.

### Следующий шаг формата: диспетчер tool-io (не в этой версии)

Отказ включать второй модуль с теми же `rewrites` — минимальная защита, но она запрещает
законную композицию: C2 (сжатие вывода) и F1 (маскирование) оба хотят `updatedToolOutput`.
Правильное решение — **один хук-диспетчер** на пару (событие, инструмент), который гонит
стадии модулей последовательно в объявленном порядке (`metadata.srednoffOs.toolIo`,
номер стадии) и возвращает Claude Code один результат. Порядок для пары C2/F1 обоснован в
C2: на выходе F1 — последний (ближе всех к модели), на входе — последний (ближе всех к
исполнению). В E1 v1 диспетчера нет; он появляется отдельной правкой E1, когда до
реализации дойдёт второй переписывающий модуль.

### Альтернативы, которые отвергнуты

- **Чистый плагин Claude Code, ставится как плагин.** Проще всего, но плагинный кэш — в
  `~/.claude/plugins`, `hooks.json` не ветвится по ОС, а включение/выключение — через
  `/plugin`, а не флагом режима, который читают хуки. Оставлено как совместимость (Q2).
- **Свой формат без `plugin.json`.** Проигрывает бесплатной возможности отладить модуль
  через `--plugin-dir` и валидировать `claude plugin validate`.
- **Хуки модулей прямо в `.claude/settings.example.json` OS.** Так сделаны нынешние хуки;
  это и есть «размазано по пяти файлам», от чего E1 уходит.

## API contracts (интерфейсы и форматы)

`installed.json`:

```json
{
  "schema": 1,
  "osRoot": "D:/1gitprog/os/srednoff-os-for-claude",
  "modules": {
    "f1": {
      "version": "0.1.0",
      "installedAt": "2026-10-01T12:00:00Z",
      "settingsFile": ".claude/settings.local.json",
      "hooks": [
        { "event": "PreToolUse", "matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash|PowerShell", "sha256": "<хэш записи обработчика>" }
      ],
      "skills": ["f1--os-filter"],
      "commands": ["os-filter.md"],
      "agents": []
    }
  }
}
```

`osRoot` — откуда поставлен модуль (чекаут форка). По нему `doctor` (O1) находит ядро OS
без глобальной установки в `~/.claude/templates`.

`state.json`: `{ "schema": 1, "mode": "enforce", "changedAt": "...", "changedBy": "os-module|command" }`.
Режим `off` — единственный способ выключить модуль; в набросках бэклога он же иногда
записан как «`enabled=false`».

Формат `doctor/checks.json` (проверки модуля: команда для `.ps1`/`.sh`, таймаут,
`critical`, объявленные порты и исполнители) определяет O1; E1 только гарантирует, что файл
есть и его путь объявлен в манифесте.

Коды выхода `os-module`: `0` — успех; `2` — отказ проверки совместимости или конфликт
`rewrites`; `3` — settings-файл не парсится (ничего не меняем); `1` — прочее.

## Data model / migrations

- `schema` в `installed.json`, `state.json` и `metadata.srednoffOs` — целое. Установщик
  знает текущую и предыдущую схемы; неизвестная — отказ с понятным сообщением, без правок.
- Обновление модуля: `install` поверх установленного сравнивает версии, переносит
  `state.json` и пользовательский конфиг, хуки пересливает (`disable` + `enable`).

## Security model

- Установщик пишет только в `<project>/.claude/` и в `~/.claude/logs/os-modules/<id>/`.
  Никаких `~/.claude/settings.json`, `~/.claude/CLAUDE.md`, `~/.claude/templates` (HANDOFF §2).
  Guard как в `init-claude-project` (v1.16): отказ, если проект = `$HOME`.
- Перед слиянием settings — резервная копия с меткой времени (так же делает
  `init-claude-project`: `.bak.<stamp>`).
- Модуль не получает секреты через `settings.json`. Чувствительные значения модуля — в его
  `stateDir` с правами только владельца, или в хранилище ОС (как `userConfig.sensitive`
  у плагинов, PF-17).
- Флаг режима пишется файлом в проекте — значит, его может переписать и модель через
  Write/Bash. Для модулей безопасности (F1) это угроза «модель выключила фильтр»; защита
  описывается в спеке модуля (у F1 — самозащита в PreToolUse).

## Risks

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Слияние в settings портит пользовательский JSON | средняя | высокое | бэкап перед записью; отказ при непарсящемся файле (код 3); сценарий run-evals на «чужие» хуки |
| Два модуля переписывают один инструмент (A-03) | средняя | высокое (молчаливая утечка у F1) | поле `rewrites`, отказ `enable`, проверка `doctor` |
| Дрейф формата плагина Claude Code | средняя | среднее | держимся полей 2.1.177, `claudeCodeCompat`, пробы O3 после обновления |
| Парность `.ps1`/`.sh` расходится | средняя | среднее | существующий CI + общий сценарный набор run-evals, гоняемый на обеих платформах |
| Мусор после `uninstall` | низкая | среднее | учёт в `installed.json`, сценарий «uninstall возвращает settings байт в байт» |

## Acceptance criteria

1. `os-module new demo` создаёт модуль, который проходит `claude plugin validate` — AC→T1.
2. `install` + `enable` + `mode demo off` → поведение Claude Code на наборе вызовов
   инструментов идентично проекту без модуля, а навыков, команд и агентов модуля в
   `.claude/` нет — AC→T2.
3. `enable` отказывает (код 2), если другой включённый модуль объявил тот же инструмент в
   `rewrites` — AC→T3.
4. `disable` + `uninstall` возвращают `settings.local.json` к исходному байт в байт, если до
   установки файл существовал; удаляют его, если не существовал — AC→T4.
5. Установщик отказывает, если целевой проект = домашний каталог — AC→T5.
6. Всё выше проходит под PowerShell 5.1 и под bash — AC→все T.
