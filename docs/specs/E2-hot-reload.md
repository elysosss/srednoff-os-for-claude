# E2: Горячая перезагрузка правил и конфигов модулей без перезапуска

> Статус: DRAFT
> Тип: спека-набросок
> Модуль E1: не модуль — часть контракта модуля E1 (обязательства для модулей с долгоживущими процессами) + CLI `os-reload`
> Зависит от: E1, F1 (первый демон)   Блокирует: —

## Goal
Правка правил или конфига модуля начинает действовать в идущей сессии Claude Code без её перезапуска, а невалидная правка **никогда** не оставляет модуль без правил.

## User value
Добавить правило маскирования F1 или выключить модуль посреди длинной сессии — без потери контекста. Закрыто, когда после правки `/health` демона показывает новое поколение конфига, а сломанная правка видна в `/os-doctor` как WARN при работающем прежнем наборе.

## Non-goals
- Не перезагрузка того, что Claude Code уже перезагружает сам (settings, хуки — PF-16; текст `SKILL.md`).
- Не админ-API по сети. У движка фильтра admin-API без аутентификации (GF-05) — этот образец сознательно не копируем.
- Не смена профиля O4, `CLAUDE_CONFIG_DIR`, env-переменных Claude в идущей сессии — это только при старте.
- Не горячая перезагрузка `CLAUDE.md` и `.claude/rules/*` (вне нашего контроля, PF-09).

## Current state
Что уже «горячее» без нас: правки `hooks`/`permissions` в settings (PF-16, с событием `ConfigChange`); скрипты хуков — новый процесс на каждый вызов, правка скрипта действует со следующего вызова; `SKILL.md` отслеживаются (доки `skills`). `/reload-plugins`, `/reload-skills` есть в 2.1.177 (строки в бинаре). Холодное — только долгоживущие процессы модулей: демон F1 `os-maskd` держит скомпилированный набор правил; у движка есть перезагружаемый реестр (GF-03), но нет безопасного способа его дёрнуть.

## Assumptions
- `ASSUMPTION:` правки `CLAUDE.md`/`.claude/rules` посреди сессии доходят до модели только после `/compact` (доки: корневой `CLAUDE.md` перечитывается после компакции) или перезапуска. Проверить спайком с маркером в правиле.
- `ASSUMPTION:` `ConfigChange` в 2.1.177 срабатывает на `project_settings`/`local_settings` так, как описано в доках (строки есть в бинаре). Проверить логирующим хуком.

## Questions
1. Может ли `ConfigChange`-хук OS **блокировать** правку settings, выключающую защитный хук? По умолчанию **нет**: только предупреждение (`systemMessage`), блок — опция модуля, выключенная по умолчанию.

## Architecture (дизайн)
Карта «что как перезагружается»:
| Объект | Механизм | Что делает E2 |
|---|---|---|
| хуки/разрешения в settings | Claude Code (PF-16) | ничего; установщик E1 пишет через temp+rename |
| скрипты хуков, `config/*.json`, флаги в `installed.json` | читаются на каждый вызов | **правило контракта**: хук не кеширует конфиг между вызовами |
| демоны модулей (F1 `os-maskd`) | нет | watcher + validate-then-swap (ниже) |
| модули через `--plugin-dir` | `/reload-plugins` | `os-reload` подсказывает команду |

**Демон: validate-then-swap.**
1. Источник — файлы конфига и правил модуля. Наблюдение — **опрос mtime+размер раз в 2 с** (FileSystemWatcher на Windows теряет события на сетевых дисках и при атомарной замене), плюс файл-триггер `reload.request` в каталоге состояния модуля.
2. На изменение: прочитать → проверить схему → скомпилировать правила → прогнать **золотые фикстуры модуля** (для F1: канарейки каждого типа данных должны маскироваться) → только при успехе атомарно подменить активный набор, `generation+1`.
3. Неуспех: активным остаётся **последний рабочий набор**; ошибка пишется в состояние. Пустой или частично загруженный набор не активируется никогда — это прямой урок `grep -P`/`jq`: тихое «правил нет» = fail-open.
4. Перезагрузки сериализуются (одна за раз); запросы во время перезагрузки обслуживаются старым набором.
5. `/health` отдаёт `config: {generation, hash, loadedUtc, lastError}`; O1 делает из `lastError` WARN, а из расхождения `hash` с файлами на диске дольше 10 с — WARN «правка не применена».

**Триггер вместо админ-API.** `os-reload [module]` создаёт `reload.request` (запись в файловую систему пользователя — уже граница доверия), ждёт роста `generation` в `/health` до 10 с и печатает результат. Сетевой ручки «перезагрузить» у демона нет.

**ConfigChange (опционально)**: хук модуля `os-core` на `project_settings|local_settings` сравнивает новые settings с ожидаемыми хуками OS; если защитный хук исчез — `systemMessage` «защитный хук X отключён правкой settings».

## API contracts (интерфейсы и форматы)
Контракт E1 для демонов — `metadata.srednoffOs.reload`:
```json
{ "watch": ["config/*.json", "rules/*.yaml"], "pollMs": 2000, "trigger": "reload.request", "fixtures": "tests/golden/" }
```
`GET /health` → `{"service":"os-maskd","instanceId":"...","config":{"generation":7,"hash":"sha256:...","loadedUtc":"...","lastError":null}}`. `os-reload [module] [--timeout 10]`: 0 применено; 1 отвергнуто валидацией (печатает `lastError`); 2 демон не ответил; 3 модуль без долгоживущих процессов (перезагрузка не нужна — это не ошибка, печатается пояснение).

## Data model / migrations
В каталоге состояния модуля: `reload.request` (пустой, удаляется демоном после обработки), `last-good/` (копия последнего применённого набора для рестарта демона), `reload.log` (последние 50 событий: время, generation, результат, без содержимого правил).

## Security model
Защищаем от: тихого fail-open при сломанной правке; открытой сетевой ручки перезагрузки (её нет); гонки полузаписанного файла (валидация отвергнет, повтор через `pollMs`). Не защищаем от: процесса пользователя, который валидно изменит правила (у него и так права на файлы); от правки, которая валидна, но ослабляет правила — это видно только в `reload.log` и git проекта.

## Risks
| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Опрос раз в 2 с ест CPU на больших наборах | низкая | низкое | хешировать только при изменении mtime/размера |
| Фикстуры медленные — перезагрузка дольше таймаута хука | средняя | среднее | запросы обслуживает старый набор, хук не ждёт перезагрузку (PF-12) |
| Модуль кеширует конфиг вопреки контракту | средняя | среднее | сценарий run-evals контракта E1 для каждого модуля |

## Acceptance criteria
- AC1 Валидная правка правил F1 применяется без перезапуска сессии, `generation` растёт (S1).
- AC2 Невалидная правка оставляет прежний набор активным, `/os-doctor` даёт WARN (S2).
- AC3 У демона нет сетевого эндпоинта, меняющего состояние (S3).

## Rollback plan
Watcher выключается флагом `reload.pollMs: 0` — демон читает конфиг только при старте (прежнее поведение). `os-reload` удаляется без последствий; `last-good/` — удаляется вместе с каталогом состояния.
